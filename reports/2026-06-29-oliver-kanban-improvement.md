## 1. 현황 진단

- 현재 kanban에 약 60건의 task가 등록되어 운영 중입니다.
- 동시에 task 생성·완료 신호·파일 생성이 얽혀 있어, **task 상태만 보고서로는 실제 산출물 상태를 알 수 없는 구조**입니다.
- 이미 확인된 결함:
  - task 완료 신호가 나왔지만 파일이 생성되지 않은 경우(Mia 등)
  - task가 spawn 실패(protocol violation)로 종료된 경우(Noah, Sam 등)
  - 중복 task가 병행되어 같은 파일을 동시에 수정하려 한 경우

## 2. 문제점 정리

| # | 문제 | 영향도 | 원인 |
|---|------|--------|------|
| 1 | task 완료 ≠ 파일 생성 | 높음 | 완료 검증 루프가 없음 |
| 2 | protocol violation 반복 | 높음 | 팀원별 실행 환경·권한이 달라 Jenkins 같은 공통 진입점이 없음 |
| 3 | 파일 경로 혼재 | 중간 | 동일 규칙이 여러 문서에 중복 기술됨(규칙/파일관리/회사개요 등) |
| 4 | 의존성 순서 무시 | 중간 | Oliver가 선후 관계를 지시서에 명시하지 않고 병행 요청함 |
| 5 | 검증 병목 | 중간 | 모든 검증이 Oliver 보고에 집중됨 |

## 3. 개선 방법 (실행형)

### 3.1 완료 정의(DoD) 강제화
```markdown
각 task는 다음을 모두 만족해야 '완료'로 간주한다:
1. 원본 경로에 산출물 파일이 실제로 존재함
2. 파일 상단 메타데이터(작성자/소유자/날짜/버전/경로)가 채워져 있음
3. 해당 파일이 다음 task의 입력으로 사용되는 경우, 입출력 관계가 기록됨
```
- 이 DoD를 `company/00-작업관리규칙.md`에 추가합니다.
- Oliver는 task 완료 신호를 받으면 위 3항을 파일 시스템 직접 확인 후 승인합니다.

### 3.2 의존성 기반 task 그룹핑
- 순서가 있는 task는 반드시 `preceded_by` 필드로 선행 task ID를 명시합니다.
- 병행 가능한 task끼리만 같은 날에 할당합니다.
- 예: 디자인 시스템 → 무드보드 → 로고 시안 순서이면, 뒤 task는 앞 task 완료 보고 후 생성합니다.

### 3.3 주간 정기 점검 task 도입
- 매주 월요일 `company/06-작업관리규칙-점검.md`를 자동 생성하는 task를 Oliver가 본인에게 등록합니다.
- 점검 항목:
  - 번호 중복 파일 여부
  - 메타데이터 누락 파일 수
  - 완료된 task 중 파일이 생성되지 않은 건수
  - protocol violation 발생 task 수

### 3.4 Slack 전파 경로 고정
- 규칙에 채널 ID `C0B8U8VK70C`를 명시하고, 채널 변경 시 규칙 업데이트 의무화합니다.
- 전파 템플릿을 사용해 알림 누락을 줄입니다(Noah 제안).

### 3.5 예외 기준 추가
